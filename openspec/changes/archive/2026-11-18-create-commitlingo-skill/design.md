# Design

## Context

Мотивация и границы change описаны в `proposal.md`. В репозитории есть каркас OpenSpec и MIT-лицензия; исходников CommitLingo, npm-пакета и тестовой инфраструктуры пока нет. Пять delta-спецификаций описывают согласованное наблюдаемое поведение, включая установку и обновление. Этот документ фиксирует архитектуру и отдельно перечисляет вопросы, которые нужно решить перед соответствующей реализацией.

Основа общей методики — [conventional-commit-message в выбранной ревизии](https://github.com/conventional-changelog/conventional-changelog/blob/0cdedf882b7d2c86ea8e03ce0c4fafc597fa2108/skills/conventional-commit-message/SKILL.md), upstream SHA `0cdedf882b7d2c86ea8e03ce0c4fafc597fa2108`. Файл и [корневой LICENSE.md этой ревизии](https://github.com/conventional-changelog/conventional-changelog/blob/0cdedf882b7d2c86ea8e03ce0c4fafc597fa2108/LICENSE.md) проверены: frontmatter скилла указывает MIT, а корневой текст — ISC с уведомлением conventional-changelog team. Это различие маркировок фиксируется явно; заимствованный материал не объявляется исключительно MIT. При импорте сохраняются исходная отметка MIT, ISC-текст и уведомления с атрибуцией. Собственная MIT-лицензия CommitLingo не заменяет сведения о происхождении заимствованного материала.

## Goals / Non-Goals

**Goals:** независимость общей методики от грамматики; одинаковое проектное соглашение при локальной и глобальной установке; явные состояния пользовательской локали; разделение готового текста, предложений настройки и Git-действий.

**Non-Goals:** отдельный сервис генерации, собственная модель или обязательный API-ключ; гарантия естественности любого языка автоматической проверкой; автоматическая публикация пакета или PR; реализация других агентов в первом варианте. Установщик — обёртка над Skills CLI; собственный механизм загрузки и размещения скиллов не разрабатывается.

## Decisions

### 1. Общая методика и языковые правила — разные слои

Согласовано: `skills/commitlingo/SKILL.md` адаптирует анализ diff, `type`, `scope`, публичного контракта и breaking changes из upstream. Языковые установки и примеры находятся в `references/locales/ru.md` и `en.md`; новые поставляемые языки добавляются рядом.

Обязательный порядок импорта: использовать upstream SHA `0cdedf882b7d2c86ea8e03ce0c4fafc597fa2108`, скопировать исходный `SKILL.md` в `skills/commitlingo/SKILL.md` без изменения текста, frontmatter и форматирования, проверить совпадение с выбранной ревизией и создать отдельный Git-коммит. Исходная отметка MIT, корневой ISC-текст и авторские уведомления сохраняются с атрибуцией; источник и upstream SHA фиксируются вне неизменённого файла скилла. Коммит содержит только импорт и сопровождающие сведения о происхождении, без адаптации и посторонних staged-изменений. После создания нужно проверить содержимое коммита и получить его SHA. Если коммит или проверка не удались, адаптация не начинается.

Только последующие коммиты меняют имя скилла во frontmatter, общие инструкции и раскладывают языковые правила по локалям. В атрибуции сохраняется SHA коммита импорта, чтобы исходное состояние можно было открыть через Git и сравнить с текущей версией по тому же пути. Если файл позднее перемещается, документация сравнения должна учитывать переименование. Простое копирование с немедленным редактированием без промежуточного коммита исключено: оно лишает пользователя отдельной точки сравнения в истории.

Альтернатива с отдельным полным скиллом на каждый язык дублирует методику и усложняет обновления. Копирование грамматики из истории ненадёжно и противоречит назначению локалей. Английское предпочтение active voice/imperative не переносится в общий слой. Правила видимости в changelog и релизного влияния upstream preset не объявляются универсальными требованиями Conventional Commits.

### 2. Проектная настройка отделена от установки

Согласовано: `<repo-root>/.agents/commit-config.json` с полем `locale` задаёт общий язык команды. Минимальная форма — `{ "locale": "ru" }`; дополнительные продуктовые поля не согласованы. Пользовательские локали находятся в `<repo-root>/.agents/commitlingo/locales/<locale>.md`. Файлы предназначены для Git и переживают обновление установленного скилла.

Повреждённый JSON настройки приостанавливает генерацию и создание коммита. Скилл показывает путь и понятное описание ошибки, предлагает исправить настройку, при необходимости выбрать язык заново. Файл изменяется только после согласия пользователя. Повреждённая настройка не считается отсутствующей и не запускает автоматический переход к истории Git.

Минимальная валидация значения: указанное поле `locale` — непустая строка с кодом языка. Неверный тип или пустая строка вызывает понятную ошибку и предложение исправить настройку с согласия, без молчаливого выбора языка по истории. Корректный, но отсутствующий код (например, `de`) не считается ошибкой типа и открывает согласованные пути выбора существующей локали или создания нужной.

Хранение командного языка в личном глобальном конфиге отвергнуто. Размещение пользовательских переводов в каталоге установленного скилла усложнило бы обновление и передачу команде.

### 3. Определение языка завершается видимым предложением

Согласованный путь:

```text
project locale --> available? --> locale rules --> message
                         |
                         v
                 choose existing / create draft

no config --> history --> confident? --> message --> offer save / choose
                              |
                              v
                         ask for locale --> save explicit choice
```

При уверенном определении сообщение появляется первым, предложение сохранить язык — отдельно. Отказ не создаёт постоянного скрытого предпочтения: следующий вызов без конфигурации снова предлагает сохранить. Выбор другого языка приводит к перегенерации; сохранение в режиме выполнения определяется объединённым вопросом из решения 5. История определяет язык, но не грамматику. Молчание не означает согласия сохранить настройку.

Согласованная начальная эвристика рассматривает до 50 последних коммитов. Из этого окна исключаются merge-коммиты, очевидные автоматические сообщения и шаблоны вроде `Initial commit`. Язык определяется по обычному тексту без `type`, `scope`, ссылок и идентификаторов кода. Автоматический выбор разрешён при наличии минимум 5 информативных сообщений и доле одного языка не менее 80%; иначе задаётся вопрос. Исключённые сообщения не увеличивают выборку за пределы окна. Примеры границ: 8 русских из 10 и 4 из 5 дают `ru`; 7 из 10 или всего 4 информативных сообщения требуют выбора. Это эвристика первого варианта, не гарантия статистической точности.

В режиме выполнения коммита предложение показывается до `git commit` и объединяет выбор языка с судьбой конфигурации; подробности описаны в решении 5. При выборе другого языка сообщение сначала перегенерируется, а сохранение и включение настройки решаются до коммита.

Автоматическое сохранение распознанного языка и предложение закрепить его только по инициативе пользователя отвергнуты: пользователь хочет заметное предложение внутри обычного пути.

### 4. Проектная локаль проходит через черновик и проверку

Согласовано: создание файла по выбору пользователя даёт английский шаблон для перевода и адаптации. Он включает грамматические правила, удачные и неудачные примеры; шаблон не активирует язык. После явного запроса проверки скилл проверяет обязательные разделы, пропуски и согласованность примеров с правилами. Успешная проверка открывает выбор языка проекта и отдельное добровольное предложение PR.

Согласованный формат — Markdown с frontmatter `locale`, `name` и постоянными заголовками `Grammar rules`, `Good examples`, `Bad examples`. Ключи и заголовки сохраняются при переводе. `Grammar rules` описывает грамматические формы, регистр, особенности description, body и пояснений в footer. `Good examples` содержит удачные сообщения разных видов; `Bad examples` — неудачные сообщения с объяснением и исправленным вариантом. Содержимое шаблона изначально английское и предназначено для перевода и адаптации. Служебные элементы вроде `feat` и `BREAKING CHANGE` не переводятся.

Минимальный каркас файла:

```markdown
---
locale: de
name: Deutsch
---

## Grammar rules

## Good examples

## Bad examples
```

Этот каркас показывает структуру, но без заполненных правил и примеров остаётся черновиком.

Метаданные проверяются отдельно от грамматики: `locale` и `name` должны быть непустыми строками; код совпадает с именем файла без `.md`, а `name` задаёт название для показа пользователю. При несовпадении или неверном типе локаль не признаётся готовой, ошибка показывается с предложением исправления с согласия пользователя.

```text
missing --> create English template --> draft --> explicit review
                                          ^              |
                                          |              v
                                          +-- issues -- check
                                                         |
                                                         v
                                                available for choice
                                                         |
                                                         v
                                                   optional PR
```

Альтернатива «файл существует — язык готов» отвергнута, поскольку шаблон может быть неполным. Подтверждение создания файла не означает согласия переключить язык или опубликовать PR. Успешная проверка привязана к конкретной версии проверяемого содержимого. После изменения этого содержимого результат больше не разрешает использование: при следующем обращении скилл сообщает об изменении и предлагает явную повторную проверку. Результат сохраняется в версионируемом `.agents/commitlingo/locale-reviews.json`, доступном между чатами и всей команде через Git.

Согласованный формат реестра:

```json
{
  "version": 1,
  "locales": {
    "de": {
      "sha256": "<SHA-256 проверенного содержимого de.md>"
    }
  }
}
```

После успешной проверки скилл записывает SHA-256 содержимого локали. Перед вычислением переводы строк приводятся к LF, чтобы CRLF/LF на Windows и Linux давали один результат. Всё остальное содержимое, включая пробелы, учитывается целиком. При последующем использовании совпадение хеша подтверждает действительность проверки; несовпадение или отсутствие записи требует явной проверки. Нормализация переводов строк — исключение из инвалидирования при правке файла. Выбранный язык остаётся в `commit-config.json`, а результаты проверки — в отдельном реестре; изменения формата настройки языка для этого не требуются.

Для реестра версии 1 `locales` должен быть объектом, а `sha256` записи — строкой из 64 шестнадцатеричных символов. Некорректные значения вызывают понятную ошибку и предложение исправления с согласия, не подтверждая проверенность локали.

Если JSON реестра повреждён, скилл показывает путь и причину, сохраняет исходный файл без изменений и не считает проектную локаль проверенной. Предлагаются восстановление из Git либо повторная проверка локали с пересозданием реестра. Пересоздание требует согласия и сохранения копии повреждённого файла до перезаписи. Восстановленные из Git записи применимы только при совпадении с текущим проверяемым содержимым локалей.

При неподдерживаемой версии схемы скилл показывает путь и причину, предлагает обновить CommitLingo и оставляет реестр без перезаписи. Новая версия формата не понижается до версии 1 через восстановление по умолчанию. Встроенные локали, не нуждающиеся в реестре, остаются доступны при его ошибке; если проектная версия перекрывает встроенную, переход к встроенной требует явного выбора пользователя.

При одинаковом коде проектной и поставляемой локали приоритет имеет проектная версия. Если она требует повторной проверки, скилл предлагает проверить её, не переключаясь молча на встроенную. Использование встроенной версии в этом случае возможно по явному выбору пользователя. Это сохраняет командные правила при обновлении CommitLingo.

### 5. Генерация и выполнение используют один выбранный diff

Первым шагом проверяется наличие staged, unstaged и новых untracked-файлов. Если их нет, скилл сообщает «Нет изменений для составления сообщения или создания коммита» и завершает вызов. Он не придумывает текст, не создаёт пустой коммит, не запускает выбор языка или предложение сохранить настройку и оставляет конфигурацию, индекс и историю без изменений. Пустой индекс при наличии unstaged или untracked не означает чистый репозиторий.

Согласовано: режим задаётся просьбой пользователя. При staged-наборе используем его, сохраняя частичную подготовку файлов. При пустом staged рассматриваем unstaged и untracked; для одной однозначной задачи просьба о коммите разрешает подготовку и коммит без повторного общего подтверждения. Несколько задач или неясный состав требуют уточнения. Режим генерации не меняет индекс и историю.

Текст сообщения строится по набору, который реально попадёт в коммит. Настройка языка сохраняется отдельно; её автоматическое включение в коммит без явного согласия исключено. Если язык определён автоматически, а настройки нет, сначала показываем подготовленное сообщение, затем до создания коммита задаём один объединённый вопрос с четырьмя вариантами:

- сохранить язык и включить настройку в коммит;
- сохранить язык отдельным изменением без включения в текущий коммит;
- продолжить без сохранения;
- выбрать другой язык.

Первый вариант одновременно разрешает включение настройки и не требует второго вопроса. Второй сохраняет файл без его включения, третий оставляет настройку без изменений. Четвёртый перегенерирует кандидат по новым правилам и возвращает к объединённому выбору до коммита. Пока ответа нет, коммит не создаётся. При готовой сохранённой локали этого шага в обычном пути нет. Это необходимый выбор языка и состава коммита, а не повторное общее разрешение выполнить уже порученный коммит.

При неудаче `git commit`, в том числе отказе pre-commit hook, скилл показывает причину и сообщает, что коммит не создан. Подготовленные изменения сохраняются без сброса индекса. Обход hooks через `--no-verify` исключён. Скилл предлагает устранить причину и повторяет попытку после её устранения, а не вслепую. Если hook изменил файлы, перед повтором нужно заново проверить фактический diff и применить обычные правила выбора набора и сообщения.

### 6. Проверки формата дополняют содержательный анализ

Согласовано: читаем проектные соглашения и доступную конфигурацию `commitlint`; при наличии установленной локальной утилиты проверяем полный текст кандидата. Успех `commitlint` не доказывает правильность типа или естественность языка. Недоступность настроенной утилиты показываем пользователю.

Без доступного `commitlint` выполняется базовая проверка на уровне инструкций скилла: структура Conventional Commits (`type`, необязательные `scope` и `!`, разделитель `: `, непустое описание), правила локали и соответствие фактическому diff, body, footers, breaking changes и известные ссылки на задачи. Учитываются ограничения типов, scope, длины и регистра, которые удалось прочитать в проекте. При успешной базовой проверке разрешены выдача сообщения и создание порученного коммита. Если проект настроил `commitlint`, но утилита недоступна, явно сообщаем, что выполнена только базовая проверка. Автоматически устанавливать утилиту не требуется; запуск `commitlint` не считается выполненным. Возможность продолжить без утилиты не отменяет необходимость разрешить обнаруженный конфликт правил.

Если правила локали и `commitlint` конфликтуют, сначала пытаемся удовлетворить оба набора: сократить текст, подобрать иную формулировку или исправить регистр без потери смысла и грамматики. Когда совместимый вариант не найден, показываем конкретный конфликт и запрашиваем решение. В режиме генерации допускается показать кандидат с отдельным пояснением проваленной проверки. В режиме выполнения коммит приостанавливается до разрешения конфликта. Самостоятельная смена локали, правка конфигурации `commitlint` и молчаливое игнорирование конфликта исключены.

Ссылки оформляются по проектным правилам. Если их нет, известная ссылка попадает в `Refs: ...`. Закрывающая ссылка требует явного намерения пользователя и соответствующего завершения задачи; автоматически придумывать задачу нельзя.

### 7. Предлагаемые технические меры для реализации

Это технические рекомендации, а не новые подтверждённые продуктовые решения: разрешать пути от Git-корня; проверять идентификатор локали и границы разрешённого каталога; сохранять существующее содержимое пользовательских файлов; перед коммитом сверять фактический staged diff с анализируемым; передавать сообщение способом, сохраняющим Unicode, переводы строк и литеральные символы shell. Реализация должна учитывать Windows/PowerShell.

### 8. Установка и обновление делегируются Skills CLI

Согласовано: npm-пакет CommitLingo предоставляет тонкую обёртку над [Skills CLI](https://github.com/vercel-labs/skills), скрывающую источник и параметры установки скилла для Codex. Используется фиксированная версия зависимости, которая обновляется после проверки совместимости. Конкретный номер зависимости выбирается при реализации по результатам проверки. Альтернатива с собственным установщиком потребовала бы поддерживать загрузку, размещение файлов и обновления; для первого релиза выбран готовый механизм.

Пользовательский интерфейс:

```text
npx commitlingo                  --> current project, Codex
npx commitlingo --global         --> global, Codex
npx commitlingo update           --> update CommitLingo in current project
npx commitlingo update --global  --> update global CommitLingo
```

Локальная установка — default по явному решению пользователя; предложенный ранее глобальный default отвергнут. Обёртка обновляет только CommitLingo в выбранной области, а не все установленные скиллы и не другую область. Настройка языка, пользовательские локали и `locale-reviews.json` сохраняются независимо от установки или обновления. Даже глобальная установка не задаёт общего языка для всех репозиториев.

Выбранный механизм Skills CLI проверяется на Windows/PowerShell, macOS и Linux; конкретные команды интеграции, версия зависимости и обработка ошибок установщика уточняются при реализации с проверкой пользовательского контракта. Этот план не запускает установку и не меняет установленный у пользователя скилл.

### 9. Стабильный релиз связывает npm-пакет и скилл

Согласовано: каждая версия npm-пакета устанавливает соответствующую версию скилла; релиз привязан к конкретному Git commit SHA. Источником установки служит стабильный релиз, а не меняющееся содержимое основной ветки. Предварительные версии автоматически не устанавливаются. `update` выбирает последний стабильный релиз и сохраняет согласованность целевых версий пакета и скилла.

При реализации нужно проверить переход от старой версии обёртки к новой целевой паре: обновление не должно нарушать соответствие версий или зависеть от изменения основной ветки. Конкретный способ получения нужной версии обёртки — техническая деталь реализации; сценарий старой версии включается в проверки установщика. Фактическая публикация npm-пакета не выполняется в рамках фиксации плана.

### 10. Проверки первого релиза разделены на автоматические и сценарные

Согласовано: CI автоматически проверяет структуру поставки и локалей, обязательные поля и разделы, корректность примеров конфигурации. Проверки не выдают наличие заголовков или успешный `commitlint` за доказательство естественности языка и правильности смысла. Инструменты и расположение проверочных файлов выбираются при реализации; стратегия уже определена.

Поведение скилла проверяется вручную в Codex на воспроизводимых одноразовых репозиториях с подготовленными diff, историей и настройками. Для первого релиза не требуется обязательный API-ключ или автоматический запуск модельных прогонов; такую автоматизацию можно добавить позже.

Протокол сценария фиксирует исходное состояние репозитория, историю/настройки/файлы, точный запрос пользователя и ответы на вопросы, ожидаемый язык, смысл сообщения, допустимые типы, нужные вопросы и разрешённые Git-действия. Перед прогоном восстанавливается подготовленное состояние одноразового репозитория; после него записываются фактическое сообщение, вопросы и изменения файлов, индекса и истории. Результат оценивается отдельно по смыслу, грамматике и соблюдению пользовательского пути и границ действий. Дословное совпадение сообщения не требуется: несколько формулировок могут быть равноценными.

Каждая реализуемая группа задач поставляет свои примеры, проверки и документацию. Сквозные проверки связывают уже проверенные части, включая установку и обновление; они не заменяют проверки ранних групп. Готовность к первому релизу требует результатов автоматических проверок и зафиксированных ручных прогонов по согласованным сценариям пяти спецификаций.

## Risks / Trade-offs

- [Смешанная история, боты и шаблонные сообщения дают ложный сигнал] -> применить согласованные окно 50, минимум 5 и порог 80% после исключений; неоднозначность приводит к вопросу, эвристика проверяется на пограничных примерах.
- [Английские правила проникают в другие локали] -> проверить общий слой на языковые установки и проверять примеры каждой локали отдельно.
- [Проверенная локаль изменена или конфликтует с поставляемой] -> SHA-256 проверяемого содержимого хранится в `locale-reviews.json` через Git; переводы строк нормализуются к LF, остальные изменения требуют повторной проверки; проектная версия имеет приоритет, переход к встроенной требует выбора.
- [Реестр повреждён или имеет неподдерживаемую версию] -> показывать ошибку и сохранять исходник; пересоздание после явной проверки требует согласия и копии повреждённого файла, неподдерживаемая версия требует предложения обновить CommitLingo вместо перезаписи.
- [Формальный `commitlint` конфликтует с грамматикой локали] -> сначала искать совместимую формулировку; при неудаче показать конфликт и ожидать решения до коммита, сохраняя правила без самовольных изменений.
- [Автоматический staging захватывает посторонние изменения] -> использовать staged-набор при его наличии; при неоднозначности уточнять; сохранять границы согласованного набора.
- [Новая конфигурация попадает в коммит неявно] -> отделить сохранение от согласия на включение в коммит.
- [Проверка локали выглядит гарантией качества языка] -> разделить проверку полноты/согласованности и человеческую языковую оценку.
- [Локальный commitlint недоступен] -> выполнить согласованные базовые проверки и явно сообщить об ограничении, не заявляя об успешном запуске утилиты.
- [Git или hook останавливает коммит] -> показать причину, сохранить подготовленные изменения без сброса индекса, не обходить hooks и проверить изменённый ими diff до повторной попытки.
- [Заимствование устаревает или теряет уведомления] -> зафиксировать SHA, источник, лицензию и документировать собственные изменения.
- [Маркировки лицензий upstream различаются] -> сохранить проверенный исходник с MIT в frontmatter, ISC-текст и уведомления с атрибуцией; явно описать происхождение, не заменяя его собственной лицензией проекта.
- [Зависимость установщика меняет поведение] -> фиксировать версию Skills CLI и обновлять её после проверок совместимости на целевых платформах.
- [Обновление затрагивает другие скиллы, область или пользовательские файлы] -> явно ограничивать цель CommitLingo и область команды; проверять сохранность конфигурации, локалей и реестра.
- [Результат зависит от текущей основной ветки или версии обёртки] -> связывать стабильные версии пакета и скилла с Git SHA и проверять обновление старой установки.
- [Ручные прогоны трудно повторить] -> фиксировать исходный репозиторий, запрос, ответы и поведенческие ожидания, оценивать смысл/грамматику/действия вместо точного совпадения текста.

## Migration Plan

Существующих пользовательских данных CommitLingo нет. До реализации обязательно создаётся и проверяется отдельный коммит неизменённого upstream-скилла. Затем реализуется и проверяется адаптация с двумя локалями и проектными настройками, после неё — путь создания локалей. Упаковка реализует выбранную обёртку над Skills CLI, локальную установку по умолчанию, `--global` и отдельный `update`. Стабильная поставка связывает версии npm-пакета и скилла с Git SHA. Проектная локаль, конфигурация и реестр проверки сохраняются при обновлении; откат версии скилла не должен удалять эти пользовательские файлы. Проверки проводятся автоматически в CI и вручную по протоколу в Codex.

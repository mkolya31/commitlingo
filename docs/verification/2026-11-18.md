## Locale lifecycle and a corrected failure

The first independent creation run exposed an instruction ambiguity: the agent
created the English template and then translated it without a separate request.
It did not activate/review/commit the locale, but that translation exceeded the
intended creation step. The reference was narrowly corrected: creation ends
with the English draft; agent translation requires a separate request.

A fresh fixture/request then left the helper's English TODO template intact,
with `locale: "de"`, `name: "Deutsch"`, no registry, unchanged setting/history,
and `ready:false`. New locale/registry files were staged under the supplied
project instruction to add new files to Git; staging is distinct from creating
a commit. No implementation file was changed by the evaluating agents.

The evaluator was then given a user-provided German translation with two
contradictory examples. It found both and recorded no review. After the user
corrected the file and explicitly requested another review, the agent recorded
SHA-256 `eb8cbf737f6781639a1bfda8456f236d5dd24ff516b6df88d7280a26fc42d1e4`.
The registry became valid and `de` ready. It separately offered a PR; declining
left the locale usable and caused no publication or history change.

For a separate-chat fixture the evaluator prepared a Git snapshot of the
reviewed locale/registry (test-setup commit `569c9be878f4f351d08997001374249380fb3af3`)
and converted line endings to CRLF. Another agent, with no prior review context,
recognized the persisted matching hash and generated
`feat: GitHub-Authentifizierungsanbieter hinzufügen` without mutations.
Appending a space changed the hash to
`68c89244e250f14e301efd3435c49a35f89a334db1a31df1cce3761e10255652`.
The next invocation asked for explicit review or language selection and generated
no candidate. It did not silently use a different language or rewrite data.
